# threads-note-autopilot - 開発ルール

最終更新: 2026-03-17

---

## 1. 絶対ルール

1. **コード即書き禁止**: コードを書く前に必ず有識者議論（セクション2）を実施する
2. **コード保全**: 既存の動作するコードを許可なくリファクタリング・削除・名前変更しない
3. **バイアス禁止**: 技術選定・設計判断に個人的好みを持ち込まない
4. **品質妥協禁止**: 動くが汚いコードは許可しない
5. **技術的異議の明示**: 問題がある場合は根拠付きで反論する
6. **エビデンスベース**: 客観的指標（テスト結果・行数・CI）に基づいて判断
7. **スコープ厳守**: フェーズ外の要求は BACKLOG.md に追記し、現タスクに集中する
8. **ハルシネーション禁止**: ファイルパス・関数名・設定値を参照する際は実在確認してから使う

---

## 2. 有識者議論プロセス

### 2.1 基本原則

**すべての実装作業の前に、有識者を召喚し多角的に議論してから進めること。**

「とりあえず書いてみる」「動けばいい」は禁止。設計・方針が固まってから手を動かす。

### 2.2 有識者の召喚

作業内容に応じて、以下のような専門家ペルソナを最低3名召喚する。

| ペルソナ | 視点 | 召喚する場面 |
|----------|------|-------------|
| アーキテクト | 全体設計・依存関係・拡張性 | 新機能追加・構成変更 |
| セキュリティ専門家 | 脆弱性・入力検証・依存リスク | 外部連携・API・認証 |
| QAエンジニア | テスト容易性・エッジケース・回帰リスク | テスト設計・リファクタリング |
| SNSマーケター | 投稿戦略・アルゴリズム・エンゲージメント | 投稿戦略・コンテンツ設計 |
| noteクリエイター | 記事設計・価格戦略・収益化 | マネタイズ・記事構成 |
| DevOpsエンジニア | CI/CD・GitHub Actions・環境依存 | ワークフロー・デプロイ |

### 2.3 議論の進め方

1. **課題定義**: 何を実装するか、なぜ必要かを明文化
2. **有識者召喚**: 関連する専門家ペルソナを3名以上指定
3. **多角的議論**: 各有識者の視点から利点・リスク・代替案を洗い出す
4. **スコアリング**: 下記基準で採点（セクション2.4）
5. **判定**: 合計スコアが **8割以上（40点中32点以上）** で実装着手を許可
6. **記録**: 議論結果とスコアを DECISIONS.md に記録してから実装開始

### 2.4 スコアリング基準

| # | 評価項目 | 配点 | 観点 |
|---|----------|------|------|
| 1 | 技術的妥当性 | /10 | 選定技術は適切か、過剰・不足はないか |
| 2 | 保守性・可読性 | /10 | 他者（将来の自分含む）が理解・修正できるか |
| 3 | スコープ適合性 | /5 | 現フェーズの目的に合致しているか |
| 4 | テスト容易性 | /5 | ユニットテスト・結合テストが書きやすいか |
| 5 | リスク・副作用 | /5 | 既存機能への影響、障害リスクは許容範囲か |
| 6 | 費用対効果 | /5 | 実装コストに見合う価値があるか |
| | **合計** | **/40** | **32点以上で着手許可** |

### 2.5 8割未満の場合

スコアが8割未満（31点以下）の場合:
- 低スコア項目の改善案を議論する
- 代替アプローチを検討する
- スコープを縮小して再スコアリングする
- それでも8割に届かない場合は実装を見送り、理由を記録する

## 3. セッション開始プロトコル

### 3.1 新規会話の開始時

毎回の会話開始時に、以下をリポジトリから直接読み込む:
全ファイルを raw.githubusercontent.com 経由で読みに行くこと。
1. docs/RULES.md - 開発ルール
2. docs/design_document_v1.0.md - 設計書
3. docs/DECISIONS.md - 過去の設計判断
4. docs/BACKLOG.md - バックログ

### 3.2 会話圧縮が発生した場合

同じ手順でファイルを再読み込みする。AIの記憶に頼らず、常にファイルが正（Single Source of Truth）。

### 3.3 セッション終了時

以下を更新してからコミットする:
- 設計書の進捗（該当する場合）
- DECISIONS.md に今回の設計判断を追記（該当する場合）
- RULES.md のファイルサイズ監視テーブル（変更があった場合）

---

## 4. 変更前の影響範囲宣言（Blast Radius）

コード変更の前に、以下を宣言すること:

1. **変更対象ファイル**: どのファイルを変更するか一覧
2. **影響を受けるファイル**: importや依存関係で間接的に影響するファイル
3. **テストへの影響**: 既存テストが壊れる可能性があるか
4. **ロールバック方法**: 問題が起きた場合の戻し方

5ファイル以上に影響する変更は、必ず人間の承認を得てから実行する。

---

## 5. ハルシネーションガード

AIがコード内で参照する名前は、すべて実在確認を行う:

- **ファイルパス**: ls / find で確認
- **関数名・クラス名**: grep で実際のソースを確認
- **設定値・環境変数**: 設定ファイルやドキュメントで確認
- **外部パッケージ**: requirements.txt に記載があるか確認

確認できないものは「未確認の想定」と明記し、確認を求めてから使用する。

## 6. スコープロック & バックログ規律

### 6.1 現タスク以外の変更禁止

AIが「ついでにこれも改善しましょう」と提案した場合:
- 即座に BACKLOG.md に追記する
- 現タスクの実装に戻る
- 人間が優先順位を判断してから着手する

### 6.2 BACKLOG.md の形式

| 日付 | 提案内容 | 発生経緯 | 優先度 | 状態 |
|------|----------|----------|--------|------|
| YYYY-MM-DD | 内容 | どのタスク中に発見 | 未定 | 未着手 |

---

## 7. 決定ログ（DECISIONS.md）

### 7.1 目的

「なぜこう実装したか」を記録し、会話が消えても設計意図を残す。

### 7.2 記録形式

**## D-001: [タイトル]**
- 日付: YYYY-MM-DD
- 背景: なぜこの判断が必要だったか
- 選択肢: 検討した選択肢の一覧
- 決定: 何を選んだか
- 理由: なぜその選択肢を選んだか
- スコア: スコアリング結果（該当する場合）

---

## 8. ファイルサイズ制限

| 種別 | 上限 | 分割検討 | 強制分割 |
|------|------|----------|----------|
| Python | 250行 | 200行超 | 250行超 |
| YAML | 150行 | 120行超 | 150行超 |
| Markdown | 300行 | 250行超 | 300行超 |

AIが1回で読めるサイズを維持すること。

---

## 9. ワークフロールール

- push後は必ずリポジトリから直接ファイルを参照する
- 会話圧縮が発生したら RULES.md を再読み込みする
- mainブランチで作業（ソロ開発）
- コミットメッセージ: feat:, fix:, docs:, test:, refactor: プレフィックス
- コミット前に必ず動作確認を実施する

---

## 10. テストルール

- 新規関数にはユニットテストを追加する
- テスト層: 純粋ロジック / 外部依存 (skip-if-no-credentials) / 手動E2E
- Threads API・Sheets API のテストはモックを使用する
